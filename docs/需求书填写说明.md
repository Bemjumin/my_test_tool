# 需求书填写说明

智能体测试的是一个已经能打开的 PyQt 程序。你交出 exe 和这份 Word 需求书即可，不需要交出源码。

智能体每次都会重新看当前窗口，再决定点哪里。需求书里不要写坐标，不要写代码里的对象名。控件只用界面上的文字，例如「保存」「金额」。

模板文件是 [templates/需求书模板.docx](../templates/需求书模板.docx)。填好的样子见 [templates/需求书示例.docx](../templates/需求书示例.docx)，示例程序叫「报销录入」。下面用这个例子说明每一节。

某一节删掉、或表格里只剩「（请填写）」，对应测试会记成「需求未写，未测」。智能体不会自己编一个预期结果。

平时只手写产品需求说明书，见 [产品需求说明书说明.md](产品需求说明书说明.md)。测试需求书由 `agent test-spec` 从产品需求说明书生成，再交给 `agent test`。

已经有一份测试需求书、还要和用户逐条核对时，不要把这份技术需求书交给用户。运行 `agent confirm --requirements 需求.docx --out 用户确认.docx`，让用户勾选能在屏幕上看到的结果。用户指出不对时，改原稿再重新生成。

## 填写时遵守

- 同一个控件全篇只用一个名字。术语表里定下来之后，后文不要换说法。
- 预期结果必须是人眼能在界面上核对的文字、表格内容、按钮状态，或者输出文件里的内容。内部变量、数据库字段不要写。
- 计算要有样例。只写「合计要正确」而没有数字，智能体不会判断对错。
- 打开文件时写清文件名。不要写「随便选一个」。程序如果靠命令行收文件，把参数写进「启动参数」，不要指望智能体去猜。
- 「适用」只能填这四个词：合法、非法、边界、全部。
- 「全部」只用于三种情况都会看到的事实，例如窗口标题仍然是「报销录入」。不要把某一次成功的样例数据标成全部。
- 多个值用中文分号分开。应当被拒绝的边界写成 `应拒绝：-1`，它会按非法输入来测。
- 步骤里写点击和菜单。具体填什么写在输入项表里，避免步骤和例子各写一遍。
- 输入项里已经有非法例子时，不要再写一套非法步骤。没有单独输入值的失败（例如空表直接点保存）才把步骤的适用填成「非法」。
- 有登录时，把登录写成功能明细的第一条。启动成功标志填登录窗口的标题。账号只写测试账号。

## 1. 封面

给这次测试命名，方便报告里识别。

| 项目 | 示例 |
| --- | --- |
| 应用名称 | 报销录入 |
| 版本 | 1.0.0 |
| exe 文件名 | ExpenseEntry.exe |
| 主窗口标题 | 报销录入 |
| 编写人 | 测试负责人 |
| 日期 | 2026-10-08 |
| 本次测试目的 | 验证报销明细的录入、合计与保存 |

真正启动哪个文件，以命令行里的 `--exe` 为准。这里的文件名写给人看。

## 2. 启动与就绪

说明程序怎样算已经打开。智能体用你在命令里给的 exe 启动，再用「启动成功标志」去认窗口。

| 项目 | 怎么填 |
| --- | --- |
| 工作目录 | 需要固定当前目录时写绝对路径。跟 exe 放在一起就写「与 exe 相同」。 |
| 启动方式 | 给人看的句子，例如「双击 ExpenseEntry.exe」。 |
| 启动参数 | 需要命令行参数时按真实参数写。没有就留空。 |
| 需要先打开的文件 | 测试前要准备好的文件。若只是放在目录里供界面去选，这里说明路径，并在输入项里写明要选的文件名。 |
| 启动成功标志 | 窗口标题里出现的文字。示例是「报销录入」。有登录窗口时，填登录窗口的标题。 |
| 如何正常退出 | 可见操作，例如「点击『退出』」。 |
| 是否需要登录 | 是或否。 |
| 测试账号 | 仅在需要登录时填写，格式如「用户名 demo，密码 demo123」。 |

## 3. 环境与测试数据

分辨率写成实际使用的桌面，例如 `1920×1080`。智能体不靠坐标点击，这项用来提醒测试时不要换一套缩放。

文件表有三列：文件角色、路径、说明。

- 输入：测试前就放好、程序只读的文件。说明里写下关键内容，例如「城市可选项包含『上海』」。
- 可改动：允许测试过程改写的文件。
- 输出：程序应当生成或改写的文件。说明里写下要核对的关键内容；真正的对错仍以功能明细里的预期为准。

路径相对工作目录。示例里保存之后应出现 `输出/报销单.txt`。

## 4. 术语

三列：业务用词、界面叫法、说明。

示例：「报销明细」在界面上叫「明细表」；「合计」在界面上就叫「合计」，是窗口底部的只读金额。后文一律用界面叫法。

## 5. 角色

模拟使用只走这一节写过的人。每个人一行：

- 角色：普通员工
- 是谁：报销人
- 要完成的事：录入一条差旅明细并保存
- 在意什么：合计是否正确、能否保存
- 不该碰到的功能：不使用管理员菜单

没有这一节，或者表是空的，模拟使用记为「需求未写，未测」。智能体不会自己发明一个用户。

## 6. 功能目录

每条功能一行，编号和后面的功能明细一致。

| 编号 | 名称 | 入口 | 优先级 | 说明 |
| --- | --- | --- | --- | --- |
| F-001 | 录入明细 | 主窗口 | 高 | 添加一条报销明细 |
| F-002 | 保存报销单 | 主窗口「保存」 | 高 | 把合计写入输出文件 |

入口写菜单或按钮上的文字。优先级填高、中、低。

## 7. 功能明细

这是智能体写用例和判断对错的依据。每个功能一节，标题用 Word 的「标题 2」，格式为 `F-001 录入明细`。增加功能时整节复制，编号不要重复。

每一节里有这些内容。

前置状态。进入这个功能之前，界面应该是什么样。示例：主窗口已打开，明细表为空。

操作步骤。三列：序号、适用、步骤。步骤用业务语言，例如 `点击「添加」`。适用填合法、非法、边界或全部。

输入项。六列：

| 列 | 含义 |
| --- | --- |
| 界面标签 | 输入框、下拉框旁边的可见文字 |
| 类型 | 文本、数字、日期、下拉、勾选、文件 |
| 必填 | 是或否 |
| 合法例子 | 应当被接受的一个值 |
| 非法例子 | 应当被拒绝的值，多个用中文分号分开 |
| 边界 | 应当被接受的边界值；若这个边界应当被拒绝，写成「应拒绝：-0.01」 |

预期结果。三列：适用、观察位置、预期。

观察位置写「明细表」「提示」「输出文件」这种人能找到的地方。预期写看得到的原文或行内容。示例：

- 合法 / 明细表 / 出现一行，事由为「出差车票」，金额为「128.50」，城市为「上海」
- 非法 / 提示 / 请输入大于 0 的金额
- 边界 / 明细表 / 出现一行，金额列等于刚才输入的金额

失败时的提示。把非法情况下弹出的原文再写一遍。功能明细里没有「非法」预期、这里也空着，则非法输入记为「需求未写，未测」，不会用合法结果去凑。

不测的分支。明确不做的路径，例如「不测附件上传」。报告里会标成需求标明不测，不算漏测。

示例里因此会得到这些用例：用合法值添加一行；金额填 `-1` 时期待那句提示；金额填 `0.01` 时期待表格里出现刚才的金额；点击保存后检查 `输出/报销单.txt`；明细表为空时点击保存，期待「请先添加明细」。

## 8. 界面与窗口

三列：名称、类型、用途。类型写窗口、对话框或菜单。名称用窗口标题或菜单路径，例如 `文件 > 退出`。不需要画布局，也不需要列出每个按钮。智能体用这一节确认「该出现的窗口有没有出现」，按钮位置以当场读到的控件为准。

## 9. 计算和数据规则

四列：规则编号、说明、输入样例、应显示的结果。

示例：合计等于明细金额之和，保留两位小数；输入 128.50 与 71.50，应显示 200.00。

规则帮助理解业务。只有功能明细的预期结果里写了要看的文字时，智能体才判断对错。没有样例数字的公式不会单独变成一条失败。

## 10. 算作明显错误的现象

只写这个应用特有的、一出现就算缺陷的情况。示例：合计为负数时，「保存」仍然可以点击。

下面这些不用在这里重复，每次都会检查：控件互相重叠、控件跑出窗口、按钮或输入框没有可见名称、文字被截断、异常弹窗、程序自己退出、窗口没有响应。

这一节是空的时，特有现象记为「需求未写，未测」，上面那些通用检查仍然会做。

## 11. 已知问题与明确不测

用两个小标题分开。

已知问题：已经接受、这次不要再当成新缺陷的现象。示例：窗口最小化后恢复，明细表的滚动位置回到顶部。

明确不测：这次不打开的菜单、不做的性能和并发。示例：不测同时打开两个程序；不测打印。

## 12. 建议时请关注

模拟用户评论什么。示例：完成保存要点的步骤是否过多；提示文案是否能看懂；金额填错之后能否改回。

这些句子进入报告的「建议」一章，不记成通过或失败。没有角色时，不会模拟使用，也不会编建议。

## 报告里会有什么

一次运行结束，报告目录里有 `report.md`、`report.json`，失败或崩溃时还有截图。

- 本次用例：按需求书展开的步骤、预期、实际点和通过或失败。
- 缺陷：明显错误和崩溃。
- 模拟使用与建议：分开写，并注明不计入通过或失败。
- 未测项：需求没写、或写明不测的部分，以及原因。
